# WhatsApp Memory Search

## Purpose

This document defines the ubiquitous language used throughout the project.

Everyone involved in the project — people, documentation, code and artificial
intelligence — must use these terms with the same meaning.

The goal is to avoid ambiguity and keep a consistent vocabulary during
development.

> The domain terms below are the English names used in the code and in this
> documentation. Some stored enum values (for example event types such as
> `propuesta` or `rechazo`) are kept in Spanish; they are glossed where they
> appear.

---

# Principles

- Every concept has a single name.
- A term never represents two different concepts.
- Domain names are independent of technology.
- The code must use this terminology whenever possible.

---

# Glossary

## Conversation

Represents a complete conversation between participants.

It is the system's main context.

A conversation contains messages, participants and derived knowledge.

---

## Participant

Person who takes part in a conversation.

Examples:

- Organizer
- Member

Each message belongs to exactly one participant.

---

## Message

Minimum unit of evidence.

Represents an individual message sent within a conversation.

A message is never modified or deleted.

---

## Attachment

File associated with a message.

Examples:

- Image
- Audio
- Video
- Document
- Sticker

---

## Evidence

Original information coming from the conversation.

Evidence is the system's source of truth.

It includes:

- messages
- attachments
- dates
- participants

Evidence never changes.

---

## Source

Origin from which the information was obtained.

Examples:

- WhatsApp export
- WhatsApp sync

---

## ImportJob

Process through which information is incorporated into the system.

It keeps imports traceable.

---

## Entity

Element identified within a message.

Examples:

- Person
- Place
- Date
- Time
- Institution
- Activity
- Money

---

## Case

Continuous topic or matter discussed in the conversation.

A Case can span weeks, months or even years.

Examples:

- Travel
- Work
- Health
- Finances
- Plans

A Case groups multiple related events.

---

## Event

Specific occurrence within a Case.

An event can involve one or several messages.

Examples:

- Proposal
- Agreement
- Rejection
- Schedule change
- Discussion

---

## Relationship

Relationship between two elements of the domain.

Examples:

- An event belongs to a Case.
- A message evidences an event.
- A participant takes part in an event.

---

## Analysis

Interpretation made by an artificial intelligence model.

It never represents an absolute truth.

It can always be regenerated.

Examples:

- Level of conflict
- Tone
- Empathy
- Formality

---

## Observation

Preliminary conclusion generated by AI.

Represents a hypothesis based on the evidence.

It may later become an Insight.

---

## Insight

Consolidated knowledge obtained from multiple pieces of evidence and
analyses.

An Insight represents a conclusion that is useful to the user.

Examples:

- Most meeting proposals were rejected.
- Disagreements increase on weekends.
- Conversations about the budget tend to be resolved quickly.

---

## Summary

Automatically generated summary.

It can represent:

- a day
- a week
- a month
- a Case
- a whole conversation

---

## Embedding

Vector representation used for semantic search.

It does not represent domain knowledge.

Its purpose is to optimize information retrieval.

---

## Search

Information retrieval process.

Types:

- Exact Search
- Semantic Search
- Timeline Search
- Case Search
- Evidence Search

---

## Agent

Component in charge of answering queries using the available knowledge.

The agent never modifies the evidence.

The agent consumes information generated by the lower layers.

---

## Reminder

Reminder generated for the user.

It always requires approval before triggering external actions.

---

## Draft

Message suggested by the system.

It is never sent automatically.

---

## Suggestion

Recommendation made by the system.

Examples:

- Reply in a more formal tone.
- Wait before replying.
- Attach evidence.

---

# Prohibited terms

The following terms must be avoided because they are ambiguous or too
general.

- Data (*Dato*)
- Record (*Registro*)
- Object (*Objeto*)
- Item
- Thing (*Cosa*)
- Information (*Información*)
- Result (*Resultado*)
- Document (*Documento*) (when it really refers to a Message)
- Chat (when it refers to a Conversation)

The specific term defined in this document must always be used.

---

# Conventions

- Domain names are written in the singular.
- Each entity represents a clearly defined concept.
- The terminology used in the code must match this document.
- Changes to the ubiquitous language must be reflected throughout the
  project's documentation.

---

# Bounded Contexts

Currently the system is made up of a single context:

- Conversation Intelligence

In the future there may be independent contexts such as:

- Messaging
- Calendar
- Reminders
- Contacts
- Notifications

Each context may have its own model and language, preventing the main domain
from growing out of control. See [`BOUNDED_CONTEXTS.md`](BOUNDED_CONTEXTS.md).

----

# Goal

To maintain a consistent language so that the domain, the code and the
documentation describe exactly the same concepts.
