# Conversation Memory Assistant

## System architecture

This document describes the project's overall architecture and the technical
decisions that guide its implementation.

The main goal is to build a system able to preserve a WhatsApp conversation,
progressively transform it into structured knowledge, and allow intelligent
queries through an AI agent.

The architecture prioritizes:

- Evidence integrity.
- Simplicity.
- Low coupling.
- Incremental evolution.
- AI cost optimization.
- Easy reprocessing when better models exist.

---

# Philosophy

Artificial intelligence is not the center of the system.

The center of the system is the conversation.

AI only transforms evidence into knowledge and helps answer questions.

The whole architecture revolves around preserving the original evidence.

---

# Architectural principles

## 1. Evidence is immutable

The original messages can never be modified.

All later operations generate new layers of information without altering the
original content.

---

## 2. Knowledge is derived

Any analysis made by AI can be regenerated.

If a better model appears, the system can fully rebuild the knowledge without
affecting the evidence.

---

## 3. Everything must be traceable

Every answer generated by the agent must be able to indicate:

- the messages used
- the related events
- the confidence level

---

## 4. Decoupled processing

Storing information never depends on AI.

First it is stored.

Then it is analyzed.

---

## 5. The agent is never the source of truth

The agent only consumes knowledge.

It never writes directly over the evidence.

---

# Layers

## Archive Layer

Responsibility:

Preserve the evidence.

Components:

- Conversation
- Message
- Attachment
- ImportJob
- Source

It never runs AI.

It never interprets information.

---

## Processing Layer

Responsibility:

Transform evidence into knowledge.

It runs after a message is stored.

Pipeline:

1. Validation
2. Persistence
3. Metadata extraction
4. Entity extraction
5. Classification
6. Event detection
7. Case association
8. Insight generation
9. Embedding generation
10. Index update

Every stage is independent.

Every stage can be run again.

---

## Knowledge Layer

Represents the system's structured knowledge.

Main entities:

- Case
- Event
- Insight
- Relationship

This layer answers most queries without having to analyze the entire history
again.

---

## AI Analysis Layer

Responsibility:

Perform analysis using language models.

It produces:

- Analysis
- Summary
- Embeddings
- Observations

It never modifies messages.

It never deletes information.

---

## Search Layer

Provides specialized mechanisms to retrieve information.

Types of search:

### Exact Search

Search by:

- text
- date
- participant
- type

---

### Semantic Search

Uses embeddings.

It is used for natural-language questions.

---

### Timeline Search

Retrieves information by time ranges.

---

### Case Search

Retrieves all the information related to a specific topic.

---

### Evidence Search

Returns original messages.

It always prioritizes evidence over interpretations.

---

## Agent Layer

Responsibility:

Answer queries using the available knowledge.

The agent never queries the database directly.

It always uses the Search Layer.

Responsibilities:

- answering questions
- generating summaries
- drafting messages
- generating reminders

---

## Interface Layer

Represents the entry points to the system.

Initially:

- REST API

In the future:

- Web UI
- CLI
- Mobile app

# Monorepo

npm workspaces (root `package.json`):

```
packages/
  core/          ← domain, pipelines and CLIs (@cma/core)
    src/         ← modules below
    scripts/     ← smoke tests, regression, diagnostics
apps/            ← deployable applications that consume @cma/core
                   (HTTP API, UI, webhook receiver)
```

`.env`, `docs/`, `.claude/`, `backups/` and `docker-compose.yml` live at the
root. Commands (`npm run verify`, `npm run sync`, …) are launched from the
root and delegated to the workspace. Runtime paths are anchored to the root
with `packages/core/src/shared/repo-paths.ts`, never to the current directory.

# Architectural decisions

## Do not use multiple agents

A single deterministic pipeline will be used.

Reasons:

- lower complexity
- lower cost
- greater traceability

---

## Decoupled AI

Every interaction with models must go through an abstraction.

Never depend directly on a specific provider.

In practice:

- The domain depends on two interfaces (`AIProvider` for completions and
  `EmbeddingBatchProvider` for embeddings, in `infrastructure/ai/provider.ts`).
- No CLI, script or use case builds a concrete provider: it asks a factory
  (`infrastructure/ai/factory.ts`), which resolves it by name from the
  configuration. The factory is the only place that knows the classes.
- Each provider declares its capabilities: how it is billed, whether data
  leaves the machine and whether it forces the output schema. Every run
  prints it and records it in the audit log.
- An engine failure is thrown and stops the run; a malformed model response
  is returned as text and rejected by the parser per message.

Which engines exist, how to choose one and how to add another:
[`AI_PROVIDERS.md`](AI_PROVIDERS.md).

---

## Evidence first

Every answer must be built prioritizing evidence over interpretation.

---

## Ready for re-analysis

The system must allow fully rebuilding:

- analyses
- embeddings
- insights
- summaries

without importing the conversation again.

# Governance Layer

## Responsibility

The Governance Layer groups all of the system's cross-cutting policies.

It is not part of the domain or of the processing flow.

Its goal is to ensure the system operates consistently, securely, auditably
and configurably without mixing these responsibilities with business logic.

This layer applies to all of the system's modules.

---

## Responsibilities

### Auditing

Record important system events.

Examples:

- Imports run.
- Queries made.
- Reprocessing.
- Errors.
- Configuration changes.

---

### Analysis versioning

All information generated by AI must be versionable.

A new model never overwrites a previous analysis.

The system keeps the full version history to allow comparisons and
reprocessing.

---

### AI configuration

Centralize the configuration related to language models.

Examples:

- provider
- model
- temperature
- prompts
- retrieval strategies
- context limits

The domain logic must never depend directly on these values.

---

### Privacy rules

Apply access restrictions to sensitive information.

Examples:

- exclude intimate conversations by default
- hide content classified as 18+
- require explicit authorization to show sensitive information

These rules can change without affecting the domain.

---

### System configuration

Centralize global parameters.

Examples:

- backup frequency
- embedding size
- indexing strategies
- reprocessing policies
- storage limits

---

### Observability

Make it easier to monitor the system.

Includes:

- metrics
- logs
- processing times
- AI consumption
- pipeline status

---

## Principles

The Governance Layer never modifies the evidence.

The Governance Layer never contains business rules.

The Governance Layer only controls how the system operates.

---

## Scope

This layer affects, across the board:

- Archive Layer
- Processing Layer
- Knowledge Layer
- AI Analysis Layer
- Search Layer
- Agent Layer
- Interface Layer

Without creating dependencies between them.

### Cost Management

Control the consumption of resources associated with artificial
intelligence.

Includes:

- tracking of tokens consumed
- cost per provider
- cost per analysis
- cost per conversation
- result reuse policies
- response caching when possible

Cost optimization is an architectural goal of the system and not a concern
of the domain.

# Final goal

To build a conversational memory engine where the evidence remains intact,
the knowledge evolves continuously and the agent acts only as an intelligent
interface to query that information.
