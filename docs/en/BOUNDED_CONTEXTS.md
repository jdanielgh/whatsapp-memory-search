# WhatsApp Memory Search

## Purpose

This document makes explicit what lies inside and outside the current
context. It is based on the "Bounded Contexts" section of
[`UBIQUITOUS_LANGUAGE.md`](UBIQUITOUS_LANGUAGE.md) and on the module list of
`src/` in [`ARCHITECTURE.md`](ARCHITECTURE.md).

A Bounded Context delimits where a model and a ubiquitous language are valid.
Outside that boundary, the same terms may mean something else.

---

## Current context: Conversation Intelligence

Today there is a single Bounded Context. The whole system described in
[`DOMAIN_MODEL.md`](DOMAIN_MODEL.md), [`AGGREGATES.md`](AGGREGATES.md) and
[`UBIQUITOUS_LANGUAGE.md`](UBIQUITOUS_LANGUAGE.md) lives inside it.

### What it includes

The modules of `packages/core/src/` (`archive`, `conversation`, `processing`,
`knowledge`, `analysis`, `search`, `assistant`, `api`) are internal
subdivisions of this single context, not separate contexts. They share the
same domain model and the same ubiquitous language.

Aggregates that live inside: `Conversation`, `Case`, `Reminder`, `ImportJob`
(see [`AGGREGATES.md`](AGGREGATES.md)).

### What stays outside (external systems, not part of the context)

* **WhatsApp** — source of evidence. It is integrated through `Source` /
  `ImportJob` and is never modeled as part of the domain.
* **The AI provider** (Anthropic API, Claude Code, local models…) — consumed
  through the AI abstraction described in [`ARCHITECTURE.md`](ARCHITECTURE.md)
  ("Decoupled AI") and [`AI_PROVIDERS.md`](AI_PROVIDERS.md). The domain never
  depends on a provider's SDK directly.
* **PostgreSQL + pgvector** — persistence infrastructure. Details in
  [`DATA_MODEL.md`](DATA_MODEL.md).

These three are *upstream/downstream* of the context but do not share its
model: a decoupled integration, not a shared language.

## Future contexts (they do not exist yet — they are only anticipated)

[`UBIQUITOUS_LANGUAGE.md`](UBIQUITOUS_LANGUAGE.md) already mentions these
names. The conditions under which it would be worth separating them are
documented here, so as not to create them prematurely:

| Future context | When to separate it | Relationship with Conversation Intelligence |
|---|---|---|
| **Messaging** | When the system starts *sending* live WhatsApp messages (bidirectional webhook), not just reading them. | Consumer of the `Draft` generated by Conversation Intelligence. Conversation Intelligence must never depend on Messaging. |
| **Calendar** | When real calendar events (not just `Event` as a narrative fact) linked to the user are managed. | Consumer of `Reminder` and `Case`. *Customer/supplier* relationship: Calendar asks for data, Conversation Intelligence does not know Calendar exists. |
| **Reminders** | If `Reminder` grows enough (notification channels, recurrence, snooze) to stop being a simple Aggregate inside Conversation Intelligence. | Today `Reminder` lives inside the current context. Separate it only if notification complexity starts to pollute the conversational domain. |
| **Contacts** | If in the future more than one conversation / more than two participants are analyzed in a structured way. | It would share `Participant` through a minimal *shared kernel* (only the identifier), not the rest of the model. |
| **Notifications** | When there are multiple output channels (push, email, WhatsApp) for `Reminder`/`Draft`. | Pure downstream; it only consumes, never writes into Conversation Intelligence. |

**Decision rule:** do not create any of these contexts until the pain of
keeping everything together outweighs the cost of the separation. For a
single-developer project with a single conversation, it is easy to
over-design boundaries that are never needed — avoid copying patterns from
large teams.

## Context map (today)

```text
        WhatsApp (external)
              │
              ▼
   ┌─────────────────────────┐
   │  Conversation Intelligence │  ← only Bounded Context
   │  (archive, processing,   │
   │   knowledge, analysis,   │
   │   search, assistant, api)│
   └─────────────────────────┘
              │
              ▼
   PostgreSQL + pgvector (infra, external to the domain)
              │
   AI provider (infra, external to the domain, via the AI abstraction)
```

There are no integrations between contexts yet because only one exists.

---

## Goal

To make explicit that the absence of multiple Bounded Contexts today is a
deliberate decision, not an oversight, and to set the criterion for
separating one when the time comes.
